# MuseAI 微信小程序前端

English version: [README_EN.md](./README_EN.md)

MuseAI 前端是面向西安半坡博物馆导览体验的微信小程序。当前交付目标是先让真机完整跑通“问卷 -> 身份 -> 路线 -> 展厅导览 -> 展品识别/搜索 -> 语音播放 -> 报告”的闭环，再进入正式上线流程。

既有导览闭环曾完成真机测试；本轮建议条、展品图片、报告指导、首页恢复条件与 UI 变更已通过本地自动化验证，仍需部署到测试服务器后在微信开发者工具和真机重新回归。后续正式上线还需完成真实数据、OCR 决策、API key 治理和发布前验收。详细执行手册见 [上线准备.md](../project_materials/docs/上线准备.md)。

## 已实现能力

- 首页入口：个性化导览、默认游客导览；只有存在可恢复对话时才出现“继续上次游览”。
- 继续上次游览触发规则：本地同一导览至少保存一组完整、非错误的“用户提问 + AI 回答”。只有 session、问卷、展厅选择、计时、单条用户消息或失败回答时不展示。
- 三步问卷：追问方向、初始判断、导览节奏。
- 四类身份：
  - 考古研究员，对应后端 persona `A`
  - 研学记录员，对应后端 persona `B`
  - 历史追问者，对应后端 persona `C`
  - 器物研究员，对应后端 persona `D`
- 身份揭示页：展示当前导览视角和展厅列表入口。
- 数据驱动路线页：以无卡片页头“展厅列表”展示 `/tour/halls` 的 active 展厅并保持后端顺序，不按人格、偏好或时长重排；只有后端明确返回 `exhibit_count=0` 的临展厅会暂不列入，旧接口缺计数字段时仍保留，永久厅不会因计数为 0 被隐藏。
- 展厅选择页：按后端开放目录顺序展示；卡片原样显示馆方 `short_description/card_description`，不再压缩、截断或补标点。缺少结构化短简介时显示固定中性说明，不读取旧 `description` 生成游客文案；卡片固定为 `154rpx` 并保持连续列表，使用 `76rpx` 弱背景图标区、`32rpx/700` 标题和 `24rpx/34rpx` 单行短简介，标题与简介内部间距 `12rpx`，无序号，“已访问”使用独立尾栏。
- 展厅导览页：
  - SSE 流式 AI 回答
  - 首条入场消息只使用所选 `/tour/halls` 的动态名称与短简介，并把短简介中的多句合并为一个完整说明；第二句统一给出具体起步动作，因此任何输入都严格为两句
  - 建议条只展示当前游客 session 的后端建议接口成功返回内容；只接受 8–18 字（生产目标不超过 16 字）、以问号结尾且有具体对象的游客口语问句，完整显示且不前端截断，并过滤维护/测试、模糊通用及学术化话术；过滤后为空或请求失败时保持为空
  - Markdown 渲染
  - AI 回答纯文本复制
  - 手动 TTS 播放
- 展品识别/搜索：
  - 文字搜索展品
  - 拍照识别 MVP
  - OCR 不可用时回退到文字搜索
  - 匹配结果可跳转展品详情
  - 真实展品目录按每页 100 条串行加载完整集合；成功空目录保持为空，生产环境不展示静态 mock 展品
- 展品图片：支持馆方绝对 HTTPS 地址和后端上传图片的同源根路径；缺少图片、协议不受支持或加载失败时使用内置默认图。
- 展品详情页：显示展品图片和结构化资料，并可围绕展品继续与 AI 讨论。
- 游览报告页：
  - 不再展示“已到访展厅”明细或数量；基础统计只保留展品、问题和时长。
  - 问题统计：按用户发送消息次数统计，不对问题文本去重，并与首页继续上次游览的 AI 对话数保持一致。
  - 展品统计：点进展品详情页即计入展品浏览；同一展品重复查看只计一次。
  - 仅可信后端 UUID 计入展品统计；本地示例、mock 和 name-only 记录不冒充真实展品。
  - 下一步怎么看：优先显示后端 `exploration_guidance.next_step` 的一条具体短建议；旧报告缺少该字段时从旧 actions 或统计确定性生成一条，不显示编号、长摘要、行动列表或复制问题框。
  - 记录摘要：离开展厅或打开报告前按展厅合并本地聊天记录，再与后端 `record_notes` 合并为可复盘笔记。
  - 基础统计
- 界面优化：保留项目原有配色及首页 hero/footer/居中构图；“定制导览”使用低圆角深棕主入口，“直接参观”使用无重边框的轻量次入口，只保留中文、细箭头和 pressed 态。问卷、人格、展厅、路线和对话页保持方角、细分隔线、低阴影简化版式，不使用装饰性英文或模糊占位文案。九厅使用深棕/陶土双色粗线极简 SVG，历史追问者使用蓝底白色粗线打开书页与大问号，运行失败时回退旧 PNG。
- 移动端适配：
  - safe-area 处理
  - 底部输入区键盘抬升处理
  - 不同屏幕尺寸的基础布局兼容

开发者工具中按以下顺序验证：

1. 清除缓存并重新编译，确认控制台没有脚本错误、资源 404 或未处理 Promise。
2. 首页无历史时不出现“继续上次游览”；普通完整回答会触发入口，但只收到“（已停止）”或以该标记结束的部分回答不会触发。重新打开后应恢复对应展厅历史；同时确认 hero/footer 未变，入口无票券/拱门装饰、英文或编号。
3. 在展厅选择页检查九厅均从各自后端 `short_description/card_description` 原样显示单行短句，卡片固定约 `154rpx`、保持连续列表、厅名与简介间距舒展、无序号且“已访问”不挤标题，粗线图标在 `56rpx` 显示尺寸下一眼可辨；进入两个不同展厅，确认首条消息严格只有“本厅看什么 + 如何开始”两句。临展增删展品或修改简介后返回本页，应看到最新目录。
4. 检查展品列表、识别结果和详情页：有图时显示远程图，缺图或模拟加载失败时切换到内置默认图。
5. 检查导览建议条只显示 8–18 字（常规不超过 16 字）且以问号结尾的具体游客问句，文字完整无省略号，不出现测试、维护、学术术语或泛化话术；旧后端仍返回长建议时全部被过滤并隐藏属于预期过渡表现，部署新版短建议后应正常出现。
6. 打开报告，确认没有“已到访展厅”明细/数量和页头“x 次问答”，只出现“下一步怎么看”与一条约 30 字内的具体建议，且没有编号、长说明、复制按钮或直接追问框；记录摘要仍为提炼内容。
7. 在“详情 -> 本地设置”关闭合法域名/TLS 豁免，使用正式 HTTPS API 完成一次完整流程；真机再复核图片、SSE、TTS、键盘和安全区。

## API 地址配置

当前小程序请求地址分散在 3 个文件中，切换环境时必须同时检查：

| 文件 | 用途 |
| --- | --- |
| `utils/request.js` | 普通 REST 请求 |
| `api/stream.js` | SSE 流式导览请求 |
| `api/index.js` | 部分直连 API、TTS、OCR、展品/路线封装 |

当前默认使用正式 HTTPS API：

```text
https://api.banpo-museai.xyz/api/v1
```

如果本机已启动后端，也可以临时切到：

```text
http://127.0.0.1:8000/api/v1
```

旧公网 HTTP 调试入口只作为紧急 fallback 或历史排查使用：

```text
http://122.152.232.190:3000/api/v1
```

HTTPS request 真机验证已通过；公网 HTTP 调试入口应在服务器侧关闭或限制访问。

正式域名在微信正式环境可用还必须同时满足：

- 域名备案通过。
- HTTPS 证书有效。
- 微信公众平台已配置 request 合法域名。
- 开发者工具关闭“不校验合法域名、web-view、TLS 版本以及 HTTPS 证书”后已完成真机 request 链路测试。

## TTS 说明

当前 TTS 是手动播放 MVP：

- 只在 assistant 消息上显示播放按钮。
- 默认不自动播放，避免博物馆公共空间突然外放。
- 同一时间只播放一条语音。
- 离开 tour 页面时停止并销毁音频上下文。
- 当前默认声线为“冰糖”，前后端都应保持一致。

仍需真机确认：

- 声线是否符合预期。
- 语速是否自然。
- 生成是否超时。
- 长回答分段播放是否稳定。

## OCR 说明

当前拍照识别是小程序端 MVP：

- 用户点击拍照识别后调用相机。
- 获取图片后调用微信 OCR 能力或本地回退逻辑。
- OCR 文本会与现有 `/exhibits` 列表做 fuzzy matching。
- 未识别时回退到文字搜索。

需要配置和验证：

- 微信 OCR 服务 ID。
- 相机权限提示。
- 用户取消拍摄时不得继续识别。
- 真机拍摄展签、展品名、弱光环境的识别率。

## 报告统计说明

前端报告页优先使用后端返回的报告字段，同时会合并本地尚未完全同步的 tour events，减少页面切换、网络波动或历史缓存带来的统计漏记。

内部仍会用以下事件维护展厅访问状态，但报告页不再展示“已到访展厅”明细或数量：

- `exhibit_question`：用户在展厅内发送消息。
- `exhibit_view`：用户点进任意展品详情页。
- `assistant_answer`：兼容已完成回答的历史事件；新统计以用户发送消息和展品查看为准。

因此用户只是进入展厅不会计入访问；只要在该展厅发送过一条消息，或点进该厅任意展品详情页，就会给展厅加上“已访问”标记。展厅数量按 canonical slug 去重。前端内部统一使用展厅信息导入的 9 个 canonical slug，展示时再转换为中文名。

问题统计按用户发送消息数计算，不对相同问题文本去重，并与“继续上次游览”显示的 AI 对话数保持一致。展品统计单独计算：用户点进展品详情页后记录 `exhibit_view`，报告中展示为“展品”，同一展品重复查看只计一次。

记录摘要的数据来源包括：

- 离开展厅时保存的本地展厅级摘要
- 打开报告时当前展厅的本地用户问题和 AI 回答
- 后端按展厅聚合的 `record_notes`
- 当前展厅和展品上下文

记录摘要只保留展厅级短笔记，避免把每个问题逐条堆叠，也避免把处理过程、兜底提示或无意义说明展示给用户。

报告指导区固定显示“下一步怎么看”，优先消费后端 `exploration_guidance.next_step`，并只展示一条约 30 字内的具体建议。页面不显示后端标题、长总结、编号、行动卡、展厅/展品 ID 或复制问题框；旧报告缺少 `next_step` 时从旧 `actions` 的首条完整行动或现有统计确定性生成一条短建议，仍会过滤“有效互动较少”“暂时不生成”等拒绝型文案。

## 展品图片说明

- `image_url` 为绝对 `https://` 地址时直接加载。
- `image_url` 为 `/api/v1/...` 等根相对路径时，前端会拼接当前 API origin；上传图片因此可与 REST API 共用域名。
- 空值、`http://`、`javascript:` 等不受支持的地址不会进入图片组件。
- 列表、识别结果和详情页统一在缺图或 `binderror` 时回退 `/assets/icons/exhibit-list-item.png`。
- 替换正式数据后需要同时验证外部图片域名是否符合微信下载/图片加载规则；优先使用已备案的 API 域名托管上传图片。

## UI 规范

界面沿用棕色、米色与陶土色体系。首页 hero/footer、居中排版和间距保持原样，“定制导览”使用低圆角深棕主入口，“直接参观”使用无重边框轻量次入口，只保留中文、细箭头和按压反馈；禁止恢复票券、拱门、门槛、英文或编号装饰。其他主要页面以方角、细分隔线、低阴影和中文层级形成简化布局。展厅图标只用单色或双色粗线/大色块，不堆叠小细节。面向游客的文字应说明具体对象与动作，不使用无信息量的英文档案标签、模糊占位语或过度学术化措辞。主要按钮和可点击卡片的触控高度不低于 `88rpx`，并继续处理 safe-area、键盘遮挡和文本可读性。

- iOS 输入框和键盘是否遮挡。
- Android 不同分辨率下底部操作区是否错位。
- 建议条是否串展厅或串展品。
- 展厅卡片是否无序号、固定约 `154rpx` 并保持连续列表，厅名与简介内部间距是否约 `12rpx`，短简介是否原样来自本行 `short_description/card_description` 并单行完整显示，“已访问”是否不挤标题；九厅粗线图标是否清楚可辨，临展增删展品或修改简介后返回页面是否刷新。
- 建议条是否只显示 8–18 字（常规不超过 16 字）、以问号结尾的完整口语问句，且不出现测试/维护话术、模糊表达、学术术语或与当前展厅/展品无关的通用问题；前后端错峰部署时旧长建议被过滤为空属于预期，不能因此放宽过滤。
- 首页在无完整问答历史或 assistant 只留下“（已停止）”时是否隐藏“继续上次游览”，完整问答落盘后是否正确出现并恢复。
- 展品绝对 HTTPS 图片、同源上传图片、缺图和加载失败四种情况是否分别正确显示。
- AI 回答是否能复制纯文本。
- TTS 播放、停止、切换、离页销毁是否正常。
- OCR 拍照取消后是否停止识别。
- 报告是否完全移除“已到访展厅”明细/数量和页头“x 次问答”，展品/问题/时长统计是否正确，“下一步怎么看”是否只有一条具体短建议且无编号/复制框，记录摘要是否为提炼内容而非问答逐条复述。

- 测试号不能等价于正式小程序发布环境。
